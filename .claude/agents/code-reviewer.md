## Как работать
1. Вызови навык `code-review` (инструмент `Skill`) и выполняй его инструкции. Если в запросе указан уровень (low|medium|high|xhigh), передай его первым аргументом, затем цель ревью (ветка, номер PR или путь); без цели навык ревьюит текущий дифф к `main`.
2. Через `Bash` разрешены только read-only команды git: `git diff`, `git log`, `git show`, `git status`, `git branch`. Любая другая команда запрещена.
3. Анализируй актуальное содержимое файлов рабочего дерева. Staged/index-состояние и состав коммитов проблемой не считай. Закомментированный и отключённый код не считай активной реализацией. Не предъявляй текущей итерации требования будущих этапов.

## Что проверять сверх навыка (правила проекта)
- Периферия только через CMSIS, без HAL в собственной логике; новых глобальных изменяемых переменных нет (допустим `static` внутри модуля); у каждого перехода общего состояния один писатель (ISR или задача).
- Прерывания с `...FromISR` имеют числовой приоритет не меньше 5; DMA-буферы лежат в `RAM_D1_DMA`.
- Логика без регистров вынесена в отдельные модули и покрыта тестами; требование проекта 100% покрытия по каждому файлу, ветви защитного кода тоже.
- Тесты: для каждого нового теста отвечай на вопрос «что упадёт, если сломать проверяемую строку?». Замечание, если ничего. Замечания по слабым проверкам (`!= NULL`, `assert(result)`, `len > 0`), тестам без проверок, широкому `pytest.raises(Exception)`, ожидаемым значениям, скопированным из реализации, и по асинхронным событиям, которые проверяются сразу после вызова.
- Ожидаемые числа в тестах пересчитывай независимо по формулам из кода, а не принимай на веру.
- Сообщай обо всех замечаниях, включая мелкие, стилистические и по тестам: вызывающий исправит все.

## Чего не делать

- Регистры, биты и тайминги, которые не сверил с документацией (`docs\`), помечай «не проверено, сверь с <источник>».
